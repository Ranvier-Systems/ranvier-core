Code follow-ups from the Rules 2/12/13/20 doc-correction pass. Canonical rule wording was updated in `.dev-context/claude-context.md` on 2026-05-05; this section tracks the code sites that violated the corrected rules. Each item landed as its own PR — they had independent scope and risk profiles.

### P0 — Reactor stalls from `seastar::async` misuse (Rule #12)

The codebase wrapped blocking SQLite and `std::ifstream` calls in `seastar::async(...)` under the assumption that this offloads to a thread pool. It does not — `seastar::async` runs in a `seastar::thread` that executes on the reactor, so the blocking call still stalls the shard. Reference fix pattern: `src/tokenizer_thread_pool.cpp` (dedicated OS worker thread + `seastar::alien::run_on` for completion signaling).

- [x] **[P0] Refactor `AsyncPersistenceManager` SQLite path to a dedicated worker thread**
  _Locations:_ `src/async_persistence.cpp:147` (shutdown flush), `src/async_persistence.cpp:284` (periodic flush), `src/async_persistence.hpp:25-44` and `src/sqlite_persistence.hpp:17-30` (false "thread pool" docstrings).
  _Justification:_ Every persisted route/backend mutation currently stalls the shard for the duration of the SQLite call. Highest-frequency offender.
  _Approach:_ Mirror `tokenizer_thread_pool` — MPSC queue drained by a `std::thread`, completion posted back via `seastar::alien::run_on`. Update the docstrings to reflect reality.
  _Verification:_ Latency measurement under sustained write load before/after in the Docker testbed.
  _Complexity:_ Medium-High (new thread, lifecycle, shutdown ordering).

- [x] **[P0] Remove blocking `ifstream` from hot config reload**
  _Location:_ `src/application.cpp:1435` wrapped `RanvierConfig::load(path)` (which called `std::ifstream` at `src/config_loader.cpp:795`) in `seastar::async`.
  _Justification:_ Hot reload stalled all shards via the subsequent `invoke_on_all`. Lower frequency than persistence but same root cause.
  _Resolution:_ Added `load_config_async()` (`src/config_loader_async.{hpp,cpp}`) using `seastar::open_file_dma` + `dma_read_bulk` with a 10MB cap. Sync `RanvierConfig::load()` was refactored to share its YAML parsing body with the async path via the new public `RanvierConfig::load_from_string()` helper, so startup callers in `main.cpp` and the unit tests retain identical behaviour. `Application::reload_config` now awaits `load_config_async(_config_path)` directly — no more `seastar::async` wrapper. Missing-file semantics (return defaults + env overrides) are preserved by catching `std::system_error{ENOENT}` from `open_file_dma`.

### P1 — Latency and lifecycle bugs

- [x] **[P1] Wire up `cleanup_shard_load_metrics()` (Rule #13)**
  _Location:_ `src/shard_load_metrics.hpp:140` — `thread_local std::unique_ptr<ShardLoadMetrics>`. `cleanup_shard_load_metrics()` is defined at line 165 but never called. The unique_ptr destructor runs at thread-exit, after the reactor has torn down.
  _Justification:_ Per the corrected Rule #13, `thread_local std::unique_ptr` only works for trivially-destructible state. If `~ShardLoadMetrics` ever touches reactor primitives (metric registrations etc.) this becomes a shutdown-order bug.
  _Resolution:_ Added a new step in `Application::stop_services()` (`src/application.cpp`) that runs `seastar::smp::invoke_on_all([] { cleanup_shard_load_metrics(); })` after `_load_balancer.stop()` and before `_tokenizer.stop()` — i.e. after both consumers (`HttpController` and `ShardLoadBalancer`) are stopped, while every shard's reactor is still alive. Mirrors the symmetric init at line 653-656. No started-flag added (resetting a null `unique_ptr` is a no-op; lazy init in `shard_load_metrics()` re-creates on demand). Today's `ShardLoadMetrics` is trivially destructible (four `uint64_t` counters + `uint32_t` shard id), so this is preventive — it makes destruction order deterministic before any future field that touches reactor state turns the latent issue into a live shutdown bug.
  _Complexity:_ Trivial.
  _Follow-up flagged:_ `stop_metrics()` in `src/metrics_service.hpp:843` is also defined but never called from `Application::stop_services()` (only from unit tests). The audit referenced it as a precedent, but the precedent itself is unwired. Deliberately not bundled here — deregistering Prometheus lambdas mid-scrape has its own risk profile.

- [x] **[P1] Wire up `stop_metrics()` (Rule #6 / Rule #13)**
  _Location:_ `src/metrics_service.hpp:843` — `stop_metrics()` is defined but never called from `Application::stop_services()`. Only `tests/unit/metrics_service_test.cpp:400,403,417` invoke it. The thread-local `g_metrics` at line 822 is a raw `MetricsService*` (not even a `unique_ptr`), so without an explicit call it is leaked at process exit and its `_metrics.clear()` / `_backend_metrics.clear()` lambda-deregistration step never runs.
  _Justification:_ The header comment at line 841 is explicit: "MUST be called before destruction to deregister metrics lambdas (Rule #6). After this call, Prometheus scrapes cannot access any metrics state." Today this is latent because the process exits shortly after `stop_services()` returns and the scrape endpoint is taken down with the HTTP servers in step 3. But it is a Rule #6 violation (lambda captures whose backing state may go away) and the symmetry with `cleanup_shard_load_metrics()` makes the gap more glaring after the §17 P1 fix above.
  _Resolution:_ Added a new step in `Application::stop_services()` (`src/application.cpp`) — step `4a3` — that runs `seastar::smp::invoke_on_all([] { stop_metrics(); })` immediately after the `cleanup_shard_load_metrics()` step (`4a2`) and before `_tokenizer.stop()`. Kept as a sibling `invoke_on_all` rather than folded into the shard-load-metrics lambda so a future async signature on `stop_metrics()` does not reshape the call site, and so attribution stays clean if a shutdown regression bisects to one or the other. No started-flag added — `stop_metrics()` already self-guards on `g_metrics != nullptr`, so shards that never lazy-initialised (and the metrics-HTTP-disabled config path) are no-ops; `metrics()` lazy-initialises on next access, preserving restart safety. Mirrors the symmetric init at line 653-656 (`init_metrics()` alongside `init_shard_load_metrics()` in the same `invoke_on_all`).
  _Scrape-race analysis:_ Two ordering preconditions had to be established. **(a) Every caller of `metrics()` is quiescent at this step.** Grepped the full caller set across `src/`: the producers are `http_controller.cpp` (the dominant user), `router_service.cpp`, `stream_parser.cpp`, and the circuit-cleanup callback registered against `HttpController` at `application.cpp:642-649`. All four are driven by `HttpController`, which stopped in step 4 (`_controller.stop()`). `TokenizerService`, `TokenizerThreadPool`, `AsyncPersistenceManager`, and `ShardedConfig` do not call `metrics()` (verified by grep — they use their own `seastar::metrics::metric_groups`), so the later steps in the chain are safe. `ShardLoadBalancer` only touches `shard_load_metrics()`, not `metrics()`. **(b) No Prometheus scrape can be in flight when deregistration runs.** The metrics HTTP server (`_metrics_server`, a `seastar::httpd::http_server_control`) is stopped in step 3 via `stop_servers()` at `application.cpp:951-964`, well before this step. By inspection of the Seastar contract, `http_server::stop()` waits for in-flight connections to drain before its returned future resolves — the existing comment at `application.cpp:870` ("Application outlives the metrics server") relies on the same property. Concern resolved by inspection; no ad-hoc barrier added.
  _Caveat:_ The drain guarantee is by reading the Seastar API contract, not from a unit test in this repo. A hot-path integration test that issues sustained scrapes during shutdown would harden this — flagged in the verification scenarios on the implementation PR but not blocking.
  _Complexity:_ Low.

- [x] **[P1] Parallelize gossip SRV lookups (Rule #2)**
  _Location:_ `src/gossip_protocol.cpp:716-729` — serial `co_await _dns_resolver.get_host_by_name(srv.target)` over an unbounded SRV record list (comment at line 727 admits it could reach 500+).
  _Justification:_ Per-discovery-cycle latency = N × DNS RTT. The `maybe_yield()` at line 728 helps other shard work but does not parallelize this loop.
  _Resolution:_ Replaced the serial loop in `GossipProtocol::refresh_peers()` (SRV branch) with `seastar::max_concurrent_for_each(srv_records, MAX_CONCURRENT_DNS_RESOLUTIONS, ...)`, where `MAX_CONCURRENT_DNS_RESOLUTIONS = 16` is a new file-local `constexpr` near the top of `gossip_protocol.cpp` (named after the `MAX_CONCURRENT_*` pattern in `local_discovery.hpp`; not reusing `K8S_MAX_CONCURRENT_ENDPOINT_OPS` because that constant is semantically about k8s endpoint mutations, not DNS A-record fan-out). The redundant `co_await seastar::coroutine::maybe_yield()` between iterations was removed — `max_concurrent_for_each` provides reactor fairness through its own scheduling. The per-target `try { ... } catch (const std::exception&) { warn(...) }` is preserved *inside* the lambda so that one failed SRV target still logs and lets siblings complete; if it escaped, `max_concurrent_for_each` would abort the batch on the first exception. The `#pragma GCC diagnostic ignored "-Wdeprecated-declarations"` push/pop scope was retained around both the `get_srv_records` call and the lambda body's `get_host_by_name` call (Seastar marks both deprecated). `discovered_addresses.emplace_back(...)` is mutated from inside the lambda; this is safe because `refresh_peers()` is gated to shard 0 (line 699), and Seastar coroutines on a single shard only interleave at `co_await` suspension points — `emplace_back` itself runs to completion between awaits with no preemption, identical to the precedent at `local_discovery.cpp:82` (`results.push_back` inside its `max_concurrent_for_each` lambda) and the same shard-0-only single-threaded cooperative-scheduling assumption. Order of `discovered_addresses` becomes non-deterministic under parallel resolution, but the immediate downstream is `std::unordered_set<seastar::socket_address> new_peer_set` (line 746) and `GossipConsensus::update_peer_list` (`src/gossip_consensus.cpp:154`), which builds an `unordered_map` keyed on address — set/map semantics are order-independent. The only ordering-sensitive step is the `MAX_PEERS = 1024` truncation in `update_peer_list`, which would non-deterministically pick *which* peers get dropped if the merged list exceeds the cap; in practice this is unreachable at the documented 500-record SRV ceiling, but worth flagging for any future deployment that pushes past 1024 discovered peers. Back-of-envelope: at N=500 records and 30 ms DNS RTT, wall-clock latency drops from ~500 × 30 ms = 15 s to ⌈500/16⌉ × 30 ms ≈ 0.96 s.
  _Complexity:_ Low.

- [x] **[P1] Pin foreign worker threads to non-reactor cores**
  _Locations:_ `src/async_persistence.cpp` (single persistence worker, post-Rule-#12 refactor), `src/tokenizer_thread_pool.cpp` (one worker per shard). Both spawn plain `std::thread` workers with no CPU affinity set.
  _Justification:_ Reactor threads are pinned to specific cores. Foreign threads with no affinity are placed by the kernel scheduler, which can land them on a reactor core and cause context-switch latency spikes when the worker is active. The deployment workaround — running with `--smp=N-1` on an N-core box so the kernel has a free core — is config-only and not guaranteed (the scheduler may still preempt). An explicit pin makes it deterministic. The tokenizer pool has the same exposure and should be done in the same change for consistency; the persistence worker is a single thread so it just needs one non-reactor core, while the tokenizer pool has `smp::count` workers and would need a different placement strategy (e.g. round-robin across non-reactor cores, or accept that they share with reactors and rely on `--smp=N-K`).
  _Approach:_ `pthread_setaffinity_np` in `start()` after the `std::thread` is constructed. Take the target cpuset from config or compute it as "all cores not in Seastar's cpuset." Side note: revisit whether `SCHED_BATCH` / nice value adjustments are also worthwhile to lower the worker's priority relative to reactors.
  _Verification:_ Same latency benchmark as the Rule #12 refactor — sustained-write load with and without the pin, looking for tail-latency differences. Confirm with `taskset -p $(pgrep -f ranvier)` that the worker landed where expected.
  _Resolution:_ Added a new translation unit `src/worker_affinity.{hpp,cpp}` that encapsulates the cpuset computation and the `pthread_setaffinity_np` call, with three explicit phases. **(a) Snapshot** the process-wide allowed cpuset by calling `pthread_getaffinity_np(pthread_self(), ...)` from the top of `main()` (`src/main.cpp`) before `app_template::run()`. The main thread's affinity at that moment is the OS/cgroup-allowed cpuset; after Seastar starts and pins reactor 0 to a single core, the snapshot can no longer be recovered, so it has to happen first. **(b) Survey** the reactor cpuset via `seastar::when_all_succeed` over a `std::vector<future<cpu_set_t>>` filled with one `smp::submit_to(shard, [] { pthread_getaffinity_np(...); })` per shard — same iterator-pair `when_all_succeed` shape already used at `shard_load_balancer.hpp:216` for `refresh_all_snapshots`, so the pattern is precedented. Each shard returns its own bitmap by value (cpu_set_t is trivially copyable POD, no FFI/foreign-malloc concerns), and the `.then` continuation unions them on the originating shard. The result is stored in a TU-local static; init is called exactly once from `Application::startup()` (`src/application.cpp`) immediately after `_sharded_config.start(...)` and before any of: `init_tokenizer()`, `init_persistence()`, or `_tokenizer_thread_pool.invoke_on_all(...start_worker)`. **(c) Pin** is a synchronous `pthread_setaffinity_np` call after `std::thread` construction in each worker's `start()` (parent-thread call via `native_handle()`, eliminating the brief startup window where the worker runs on the inherited reactor core before pinning itself). Placement: worker `i` pins to `non_reactor_cores[i % M]` — round-robin with wrap. Persistence is a single worker so it passes `worker_index=0` (deterministic first non-reactor core); tokenizer-pool workers pass `_shard_id` for round-robin across shards. **Source of cpuset:** auto-derive only, no config knob. Rejected the hybrid because the operator workaround (`--smp=N-1`) is itself the forget-to-set-it failure mode this change is meant to eliminate — adding a `worker_cpuset:` field would recreate the same gap. Hard isolation across co-tenants is a deployment-layer concern (cgroup cpuset, taskset on the parent), not an in-process knob. **M=0 fallback:** if every allowed core is a reactor, the helper logs a single warn-level message at init plus a one-shot warn (via `std::call_once`) on the first pin attempt, returns false, and the workers continue with inherited affinity. Not fail-stop — operators running `--smp=N` knowingly take the latency hit. **Platform gating:** the entire mechanism is wrapped in `#if defined(__linux__) && defined(__GLIBC__)`; on non-Linux the snapshot logs an info line and every pin returns false. No build break. **SCHED_BATCH / nice deferred:** orthogonal syscall (`sched_setscheduler` / `setpriority`), separate risk surface; revisit only if measurements after this change still show reactor-vs-worker priority inversion. **CMake:** `src/worker_affinity.cpp` added to `ranvier_server`, `async_persistence_test`, `tokenizer_thread_pool_test`, and `application_test` (the latter three pull in the worker source files that now call into the helper). Unit tests that don't go through `main()` / `Application::startup()` hit the "init not yet run" early-return in `pin_worker_to_non_reactor_core` — same end-state as M=0, no test surface change. **Race-freedom note:** init is awaited once on shard 0 before any of the per-shard `start_worker` calls fan out via `invoke_on_all`; the future-chain `.then` after init imposes happens-before on the writes to `g_non_reactor_cores` and `g_init_done`, so the per-shard pin calls observe a fully-initialised vector without explicit atomics — same single-writer-then-many-readers pattern used elsewhere in this codebase for startup-initialised globals (e.g. the routing config build at `application.cpp` step 5).
  _Complexity:_ Low (one syscall per worker), but the shared design decision across persistence + tokenizer pool needs a brief writeup before coding.

### P2 — Cleanup

- [x] **[P2] Drop unnecessary `do_with` in coroutine broadcasts (Rule #20)**
  _Locations:_ `src/router_service.cpp` — `RouterService::broadcast_gpu_load` (was line 3494, now 3533) and `RouterService::broadcast_cache_headroom` (was line 3517, now 3556). Line numbers drifted between when this entry was filed and when it was actioned; the symbol-name locations were authoritative.
  _Justification:_ Both are already inside a coroutine; the coroutine frame already keeps `shared` alive across the awaited `invoke_on_all`. The current `do_with` adds no safety, just noise. Per the corrected Rule #20, coroutines are the preferred pattern.
  _Resolution:_ Replaced `co_await seastar::do_with(std::move(shared), [](auto& shared) { return seastar::smp::invoke_on_all([&shared] { ... }); });` with `co_await seastar::smp::invoke_on_all([&shared] { ... });` in both functions. `shared` (a `seastar::foreign_ptr<std::unique_ptr<absl::flat_hash_map<...>>>`) stays as a local in the coroutine frame; the inner lambda captures it by reference and is invoked-and-awaited on every shard via `invoke_on_all`, so the reference target outlives the call by construction. No move into `do_with`'s internal storage, no extra heap indirection, no second lambda layer. The preceding 4-line comment that explicitly justified the `do_with` ("makes the lifetime guarantee visible and resilient to future refactoring") was the textbook case of Rule #20's defensive over-engineering and was replaced with a one-line `// Rule #20:` reminder. The companion `broadcast_load_snapshot` site at line 3438 uses `return seastar::do_with(...)` from a non-coroutine future-returning function, so `do_with` *is* still needed there (Rule #20's correction applies only inside coroutines) — deliberately not touched. The `#include <seastar/core/do_with.hh>` at line 13 is still needed because seven other call sites in this file remain (1896, 2991, 3201, 3259, 3438, 3588, 3884 — all either non-coroutine returns or `do_with`-around-`seastar::async` patterns out of scope here).
  _Complexity:_ Trivial.

### Optional follow-up

- [x] **[P3] Add CI grep for `seastar::async(`**
  _Justification:_ The misuse was systemic enough that a lint will catch the next instance faster than another audit. Allowlist the legitimate sites once they're identified.
  _Resolution:_ Added `scripts/lint-seastar-async.sh` and a tiny `.github/workflows/lint-rule12.yml` workflow that runs it on every push and PR. The lint scans `src/` and `tests/` for `seastar::async(` occurrences and classifies each: pure-comment lines (doxygen `*` continuation, single-line `//`, or `seastar::async(` only appearing inside an inline `//` comment) are ignored automatically; real call sites must carry a `// rule12-allow: <reason>` marker on the call line OR in the contiguous block of comment lines immediately above it (walks upward through `//` and `*` lines until the first non-comment line, then stops). Allowlist-by-inline-marker rather than separate file keeps the rationale next to the code and survives line-number drift across refactors. **Surveyed call sites at land time (both marked, both legitimate):** `src/crypto_offloader.hpp:327` — this IS the codebase's offload primitive; the `seastar::thread` frame is what lets the caller's `func` use `.get()` on Seastar futures inline. `src/gossip_transport.cpp:231` — large-fanout DTLS broadcast, bounded by `_broadcast_sem` (§17 P3 above), uses `seastar::thread::yield()` for reactor fairness inside the send loop. The marker comment on each notes the rationale and, for gossip_transport, cross-references the follow-up architectural refactor (replace with coroutine + `co_await maybe_yield()` to drop the 128 kB stack entirely). **Doc mentions:** five existing references to `seastar::async()` in comments (in `src/sqlite_persistence.hpp`, `src/async_persistence.hpp`, `src/application.cpp`, `tests/unit/application_test.cpp`, `tests/unit/gossip_transport_ownership_test.cpp`) all sit on comment-prefixed lines or inside inline comments and are filtered by the lint's classifier without needing markers. **Script design:** plain `grep -rn` over the scan paths (not `git grep` — chose plain grep so the lint also catches untracked `.cpp` files added in the same commit being linted). Includes restricted to C/C++ source extensions. Tested locally against a synthetic violation (`src/lint_test_violation.cpp` containing `return seastar::async(...)`); lint correctly exited with code 1 and a clear error message pointing the author at Rule #12 and the marker convention; cleanup left the tree passing again. **Workflow:** pure shell job, no Docker, 5-minute timeout, triggers on `push` to main + every `pull_request` + manual `workflow_dispatch`. Intentionally separate from the heavier `unit-tests.yml` / `sanitizer-tests.yml` so the lint signal is visible quickly. **Failure mode:** lint exit 1 fails the CI job with a multi-line error message that lists each offending file:line, explains why `seastar::async` is the anti-pattern, points at the canonical Rule #12 doc and the BACKLOG audit, and shows the marker template. Authors who hit it have everything needed in the failure output. **Scope discipline:** kept this to a single shell script + workflow file with no dependencies (no Python, no JSON allowlist, no separate config). The marker comment IS the allowlist entry. A post-merge audit hardened the script: fixed a single-file-invocation misparse (grep without `-H` omits the filename prefix on single-file input, causing `IFS=: read` to align on `seastar::`'s own colons), simplified the comment-line classifier to a single `case` pattern, added `/* ... */` inline-block stripping, and documented the "blank line breaks the walk" invariant. Verified by a 12-case regression suite.

- [x] **[P3] Bound concurrency on gossip broadcast async path**
  _Location:_ `src/gossip_transport.cpp:208-261` — the `seastar::async` batch branch is gated only by `_gossip_task_gate`, which guards shutdown ordering, not holder count.
  _Justification:_ Per-request callers (`broadcast_cache_eviction` via `http_controller.cpp:3704`, `broadcast_route` via the route-announcement path) can in principle stack arbitrarily many `seastar::thread` instances (128 kB stack each, virtual). Unlike `CryptoOffloader::max_queue_depth` at `crypto_offloader.hpp:94`, there is no explicit cap or inline fallback. Currently self-limits because the encrypt+send block is short, but the bound is implicit.
  _Approach:_ Wrap the branch in `with_semaphore(_broadcast_sem, 1, ...)` with a small cap (4-8), or mirror the CryptoOffloader inline-fallback pattern at `crypto_offloader.hpp:284-310`.
  _Resolution:_ Added a per-`GossipTransport` `seastar::semaphore _broadcast_sem{BROADCAST_CONCURRENCY_CAP}` with `BROADCAST_CONCURRENCY_CAP = 4`. The large-fanout DTLS branch in `GossipTransport::broadcast()` now acquires one unit via `seastar::try_get_units` (fast path) before the `seastar::async` invocation; if the fast path fails, increments a `_crypto_broadcasts_waited` counter and falls back to `co_await seastar::get_units(_broadcast_sem, 1)`. RAII `semaphore_units<>` release the unit when the local goes out of scope after `co_await seastar::async(...)` resolves — Rule #19 compliant, exception-safe via stack unwind. **Cap rationale:** 4 = max ~512 kB virtual stack reservation at peak (4 × 128 kB), large enough to absorb normal eviction-burst behaviour without forcing serialization, small enough that the bound is meaningful. The plaintext and small-DTLS (≤10 peers) branches stay unchanged — both are already bounded by `parallel_for_each(peers, ...)`, and the small-DTLS path uses `CryptoOffloader` inside `send()` which has its own cap. **Operator-visible metric:** added `cluster_crypto_broadcasts_waited` Prometheus counter (production metric, not behind `RANVIER_DEBUG_METRICS`) registered in `GossipService::register_metrics` (`src/gossip_service.cpp`) alongside the other `cluster_dtls_*` and `cluster_crypto_*` counters. Operators can see backpressure activations by watching this counter's rate. **Choice of semaphore over inline-fallback:** the BACKLOG entry listed both. The inline path would need to be rewritten as a coroutine with `co_await maybe_yield()` between iterations to avoid stalling the reactor for the encrypt-loop's duration (Rule #12 — `seastar::async` doesn't actually offload to a thread pool, and the inline equivalent without the `seastar::thread::yield()` calls would stall) — that's most of an architectural rewrite (option 3 from the design note) and goes beyond P3 scope. Semaphore is simpler, matches Rule #19's idiomatic acquire pattern, and broadcasts are background work where bounded await latency is acceptable. **Scope discipline:** the existing `seastar::async` wrapper is intentionally kept — there's a separate latent issue that `seastar::async` runs on the reactor (Rule #12) rather than offloading, so the encrypt loop is a reactor-stall risk independent of stack accumulation. Filing the seastar::async → coroutine refactor as a follow-up rather than bundling here. Removed the in-code TODO at line 208 that pointed at this BACKLOG entry. Build verification user's responsibility per `.dev-context/claude-context.md` (sandbox cannot run Seastar).
  _Complexity:_ Low.
  _Cross-ref:_ In-code TODO at `src/gossip_transport.cpp:208` removed in this change. The seastar::async → coroutine refactor of the encrypt loop (drops the 128 kB stack entirely) is a separate latent issue, not bundled here.
